# ROM reload lifecycle stability evidence

Date: 2026-09-24 (Asia/Seoul)

## Outcome

Status: `RELATED_DEFECT_FIXED_ORIGINAL_SYMPTOM_UNCONFIRMED`.

The investigation confirmed and fixed several related defects in synthetic, production-linked tests: inconsistent BIOS entry-PC/MMU selection; acceptance of a short BIOS read; accepting a failed save-file read, allowing later persistence to overwrite valid save bytes with zero-initialized RAM; and nondeterministic per-instance state on fresh initialization. The teardown order was also hardened so NiFi is stopped before ROM/Gameboy destruction. These findings do not reproduce or classify the reported physical “BIOS-like” freeze. No real DS/DSi execution was performed, and no evidence establishes a memory leak, fragmentation, use-after-free, or actual IRQ/radio race.

## Test scope and results

The pre-existing host runner (`tools/run_host_tests.py:17-52`) compiles isolated command blocks from `.github/workflows/core-regression-tests.yml`. Existing examples such as `tests/rom_layout_test.cpp` test layout helpers and `tests/state_validation_test.cpp` test validators/synthetic bytes; they do not link the manager, Gameboy, RomFile, DS IRQs, or platform file lifecycle. These helper passes were not treated as full reload proof.

The added `tests/romfile_bios_lifecycle_test.cpp` links production manager, Gameboy, MMU, RomFile, CPU, mapper, SGB, and protocol code. The host adapter replaces FileHandle, UI, sound, graphics, and NiFi callback boundaries. Final candidate coverage includes 1,000 alternating synthetic GB/GBC manager load/unload cycles; BIOS on/off policy and short/missing/wrong-size/seek failures; SGB mode; one successful chooser transition; 10 shared-ROM local-link focus swaps; double unload; RAM save persistence; RAM and MBC3 clock-read failure/retry; GBS load; and valid/corrupt save-state load/retry. A fresh Gameboy instance's storage is deliberately poisoned before first save-read failure with autosave enabled; production SRAM write/autosave update/sync/unload is then exercised, and the synthetic `0x5a` save survives and reloads with zero stub handles. BIOS opcode coverage executes synthetic SCF/CCF through production `runOpcode` after mirroring the CPU context-copy boundary. The harness records stub FileHandle balance and a stubbed NiFi stop-before-destruction assertion. It does not run real FAT, a peer/link transfer, async radio delivery, DS IRQ/VBlank/FIFO scheduling, first-frame rendering, authentic BIOS code, chooser cancel, or the user's reported sequence. GBS header/init behavior is stubbed; `gbsLoadSong`, BIOS policy value 1, and FF50 are not covered by the final targeted tests.

## Resource, async, and failure boundaries

The harness observes its host FileHandle wrapper returning to zero and checks main/secondary ROM pointers and `externRam` teardown. It does not provide production allocation/byte counters, fragmentation/largest-free-block measurements, or evidence sufficient to classify a heap leak. RAM/SRAM is allocated and released in tested production objects, but those cases do not establish whole-process balance on hardware. No UAF was observed; it was not comprehensively ruled out.

Source review found `mgr_loadRom` formerly unloaded before stopping NiFi. `mgr_unloadRom` now stops NiFi first. In the DS implementation, stop removes the packet handler and disables WiFi, then performs the existing bounded VBlank waits before deinit. The ordering fix is tested through a stub but real callback context/completion was not measured. The VBlank task queue (`platform/ds/arm9/source/gbgfx.cpp:421-425, 479-484`) uses a vector from enqueue and IRQ-side copy/clear; reviewed tasks are bare function pointers, but concurrency behavior was not reproduced or changed. No IRQ/VBlank/FIFO defect or radio race is confirmed.

Still NOT RUN: allocation/open failures; write/flush/truncate failures and dirty-data retry behavior; chooser cancellation; real local-link peer and focus exchange; NiFi packet crossing teardown; DS IRQ/VBlank/FIFO behavior; real ROM first frame; real save/state I/O fault response; heap fragmentation; hardware screen classification. `saveGame`/autosave still use void write/flush APIs, so persistence failure policy remains an open separate check. No previous release was assumed good, and no historical release comparison is claimed.

## Data protection and minimum hardware follow-up

All harness inputs were synthetic ROM/BIOS/state/save fixtures in temporary test paths. No user ROM, BIOS, or real save was attached to a writing test. The diagnostics and downloaded artifacts remain under ignored `.codex-tmp/rom-reload-diagnostics/`; no archive, backup, release, or user data was removed or changed by this evidence review.

Minimum user-side follow-up when a suitable DS/DSi is available: keep a copy of the original save outside the device; install the corresponding candidate binary, verify its SHA-256 above, and keep the same binary fixed across comparisons; record device model, launcher, actual DS/DSi mode, and BIOS setting. Use the same two known-good ROMs from the user's own library (different sizes, plus same-ROM reload) with a fixed sequence; count up to 100 exit/reload cycles or stop at first failure; capture screen/text and iteration; repeat BIOS off and on as separate runs, then a short run with local/NiFi link disabled. Preserve the original incident log/save and stop if save contents change unexpectedly. Report iteration, ROM hashes (not ROM data), save/state presence, configuration, and visible message. A confirmed hardware result requires this actual repeated exit/reload procedure, not the synthetic harness.
